I spent a week last month untangling a single integration between two services that should have been straightforward. The root cause wasn't a bug. It was an API surface that made the wrong things easy and the right things undocumented.

The endpoint accepted a flat object with seventeen optional fields. Six of them were mutually exclusive in practice but not in schema. Three had naming collisions with fields in a different endpoint that behaved differently. The error messages were generated by a generic validation layer and explained what failed, but never why.

## Contracts are promises

An API is a promise. When you change a response shape without versioning, you're breaking a promise you didn't know you made. When you accept ambiguous input, you're making a promise you can't keep.

The teams that get this right treat API changes the way infrastructure teams treat production changes: with review, with deprecation windows, with clear migration paths. They don't let convenience for the server become confusion for the client.

## Error messages are part of the interface

A 400 Bad Request with a generic body is technically correct and practically useless. The caller still has to guess what happened. Was the field missing? Malformed? In conflict with another field? The server knew and chose not to say.

Good error messages name the field, describe the constraint, and suggest the fix. They're an investment in every integration that follows, because every confused developer will open a ticket, start a thread, or add defensive code against a behavior they don't understand.

## Consistency is a form of kindness

If your list endpoints paginate with `limit` and `offset`, don't make the next one use `page` and `per_page`. If you use snake_case in one service, don't switch to camelCase in another because the framework defaults that way. These aren't aesthetic preferences. They're cognitive overhead you push to every consumer.

The best API designers I've worked with have a mental style guide they apply without exception. They'd rather argue about naming conventions once than explain inconsistencies forever.

## The real cost

Bad APIs don't cause outages. They cause drag. Every ambiguous field, every inconsistent pattern, every silent behavior is a small tax on every integration, every debugging session, every new developer's onboarding. The tax compounds. The API outlives the team that wrote it. Design accordingly.
